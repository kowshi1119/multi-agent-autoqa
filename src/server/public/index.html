1d. Read-only workflow discovery

Needs verified login conditions (1c, then an Authentication only run). Sign in locally; AutoQA lists links on the landing page and opens each in-scope, read-only one once to observe a heading. On up to two list pages reached this way it also looks for record detail links, filter and pagination links, and GET search or filter forms; a form is submitted only when its GET endpoint is in the profile's allowed form endpoints and its kind is allowed — otherwise it is listed as needing your configuration and not submitted. Each draft includes a reset back to its starting page and asserts the outcome (query, result change, identity), not just the click. Links that look state-changing (delete, send, transfer, pay, approve, log out…) or leave the approved scope are listed as skipped and never opened. No screenshots, traces or page text are kept; credentials are cleared after submission. Discovery does not execute or verify workflows: confirm the drafts you want, save them, then run them.

1e. Regression suites

A suite is a named, approved selection of saved workflows and declared checks (never discovery drafts). Choosing one here makes Start run exactly that suite. A suite can only lower the profile's limits, never widen its scope. Its decision (PASS / FAIL / INCOMPLETE) applies only to that suite.

1f. Requirements and API contracts

Requirements are yours: write the acceptance criteria and link each one to assertions of approved workflows or checks. Saving creates a draft; only an approved revision counts in coverage, and editing an approved requirement creates a new draft revision. Suggestions only restate existing assertions. Nothing here is sent to any model.

Import an API contract (OpenAPI 3.0, JSON)

Supported: OpenAPI 3.0.x JSON; local #/components/schemas references; type, properties, required, items, enum, nullable. Other schema keywords are reported as unsupported and never pass. The contract's servers are ignored: checks run only against this application's approved origin and paths. Only GET operations can be approved, and nothing runs until you run a suite.

1g. API observation → checks → UI–API comparison

Signed-in runs passively record the structure of the application's own API responses (names and types from samples, never values) — an observation, not an API contract. Stages: Observed (seen in a run) → Drafted (proposed here, nothing saved) → Approved (you saved it) → Executed (a suite ran it) → Verified (its assertions passed in that run). Observed traffic never authorizes a request by itself, and a GET seen from the app is not thereby shown to be free of side effects.

Propose assertions from an executed check

For compressed APIs, a passive observation records metadata only. After a suite has run an approved structure-only check, its recorded structure (names and types of one response, never values) can support further proposals. No request is sent to make them. Approving changes the check, so suites that select it must be saved again.

Declare a UI–API comparison

Supported: a table on the page a saved workflow reaches, compared with an approved GET check that uses structure-only evidence. Relations: normalized text equality, status equality, or row count of the same page. Money and dates are not supported. "Rendering response" compares the table with the response the page itself fetched while rendering; "Separate check" sends the approved check after reading the page (not an atomic snapshot). A mismatch fails only when a second observation of both sides reproduces it with unchanged data.
